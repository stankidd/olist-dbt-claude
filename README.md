# Building a Production dbt Pipeline with an AI Agent — and What It Actually Takes

This repository is a working dbt pipeline on the [Olist Brazilian e-commerce dataset](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce), built end-to-end by driving [Claude Code](https://www.anthropic.com/claude-code) against a dbt project connected through the [dbt MCP server](https://docs.getdbt.com/docs/dbt-ai/about-mcp). It runs on DuckDB, so you can clone it and reproduce every number below in under fifteen minutes with no cloud account.

The repo is the evidence. This README is the point.

Most claims about "building pipelines with AI" are unfalsifiable — a screenshot, a demo, a LinkedIn post. This is the opposite: a public repo you can run, a build you can time yourself, and an honest accounting of where the agent needed a human. If you only read one section, read [Where It Needed a Human](#where-it-needed-a-human) — that section is why anyone should believe the rest.

---

## What I built, under what constraint

A medallion-architecture warehouse — bronze (staging) → intermediate → silver → gold (marts) — over the nine Olist source tables, covering roughly 100,000 orders placed in Brazil between 2016 and 2018.

**Twenty models, four business domains:**

| Layer | Count | What it does |
|-------|-------|--------------|
| Bronze | 9 | Parse and rename each source table. No business logic. Materialized as views. |
| Intermediate | 2 | Geolocation deduplication and payment-type resolution. |
| Silver | 5 | Join, enrich, apply business rules. Materialized as tables. |
| Gold (marts) | 4 | `mart_orders`, `mart_customers`, `mart_sellers`, `mart_reviews`. |

**The constraints I set before starting:**

- Hard cap of four marts. More would be padding, not signal.
- Every model gets tests. No model merges without them.
- All SQL must be portable — `{{ dbt.datediff(...) }}`, not raw `DATEDIFF` — so the same models compile against Snowflake or BigQuery later without a rewrite.
- The whole thing must run on DuckDB from a relative path, so a stranger can clone and build with zero credentials.

The dataset was chosen deliberately. Nine related tables with a real go-to-market shape — order funnel, customer cohorts, repeat-purchase behavior, seller performance, review sentiment — is structurally close to the kind of e-commerce work this pattern is actually used for. It is not a toy.

## The workflow — what I drive, what I never let it touch

The agent does not free-wheel. The process is deliberately gated, and the gates are where the engineering judgment lives.

**1. Business Requirements Document, written first, by me.** Before any SQL, a BRD defines every metric, every grain, every business rule — what counts as a valid order, how GMV is calculated, what makes a customer a repeat customer, how the geolocation table must be deduplicated before it is joined. This is the contract. ([see the BRD](.claude/project_docs/client-olist/03-requirements/olist-brd.md))

**2. Technical specification, generated by the agent, reviewed by me.** The agent reads the BRD, profiles all nine source tables against live data — row counts, null rates, categorical domains, referential integrity — and produces a full technical spec: exact column mappings, materializations, test definitions, and a Definition of Done. Critically, this step surfaced ten deviations from my BRD's assumptions (customer grain, review grain, seller-tier thresholds, payment-type resolution) that only became visible by profiling the real data. I reviewed and approved the spec before a single model was written.

**3. Build, layer by layer, agent-driven.** With an approved spec, the agent writes each layer, runs `dbt build` through the MCP server, and self-corrects on failures — querying the data to understand a problem, fixing the SQL, and rerunning without me touching the terminal.

**4. Human review at the gate.** Nothing reaches `main` unmerged. The work went up as a [pull request](https://github.com/stankidd/olist-dbt-claude/pull/1), reviewed, then merged.

**What I never let the agent decide:** the metric definitions, the grain of any model, the business rules, or what "correct" means. Those are specified up front and are not negotiable mid-build. The agent's job is to implement a spec faithfully and catch its own mechanical errors — not to invent the requirements. That division is the whole game.

## Where it needed a human

This is the section that makes the rest credible. Two things needed intervention. Neither was a data-modeling error, and that distinction matters.

**1. A missing dependency the spec assumed was present.** Three bronze models use `dbt_utils.generate_surrogate_key` for composite keys, but the repo had no `packages.yml` at all — so the first compile failed. The fix was mechanical: create `packages.yml`, run `dbt deps`, continue. It never reached a real build failure because the agent caught it at compile time. But it is exactly the kind of environmental assumption a spec makes silently, and a human notices immediately.

**2. A dbt version deprecation the agent's training predated.** After the first bronze-plus-silver build passed clean, dbt 1.12 surfaced a `MissingArgumentsPropertyInGenericTestDeprecation` warning on all eleven custom-argument generic tests — this version requires test arguments nested under an `arguments:` key, a change newer than the patterns the agent reached for by default. I had it fix all eleven and rebuild to zero warnings before moving on.

**The honest read on this:** the agent wrote twenty models with correct business logic on the first attempt, and the only two things that needed a human were (a) an environment gap and (b) a framework change newer than its defaults. That is a real and useful result — but note *why* the logic was right on the first try. It was not because the agent is infallible. It is because the spec was validated against live data first, which is the single highest-leverage thing a human does in this workflow.

**The defect classes I was specifically watching for** — and did not hit here, because the spec caught them earlier:

- **Join grain fan-out** — the classic silent revenue-doubler. The geolocation table has 1,000,163 rows but only 19,015 distinct zip prefixes. Joined naively, it multiplies every customer and seller row. The spec mandated deduplication to one row per prefix in an intermediate model; the build held at exactly 19,015 with zero downstream multiplication. This is the bug that looks right, runs clean, and quietly corrupts every number — and the reason the grain rule was written into the BRD before any SQL existed.
- Hallucinated columns — prevented by profiling every source table before writing SQL.
- Tests that pass but assert nothing — prevented by defining test intent in the spec, not letting the agent choose tests after the fact.

A different dataset or a looser process would surface more. The point of showing my numbers is not that AI-built pipelines are defect-free — it is that a gated, spec-first process moves the defects to where a human can see them cheaply, before they reach a mart.

## Guardrails

The process only works because the guardrails are real, not decorative.

- **Tests are merge gates.** 121 tests, and the Definition of Done requires zero failures and zero warnings before anything is considered complete. The second rework item existed *because* a warning is treated as a stop condition, not a shrug.
- **Nothing merges unreviewed.** Every change went through a [pull request](https://github.com/stankidd/olist-dbt-claude/pull/1) reviewed by a human before merge. The agent has no path to `main` on its own.
- **The spec is the contract.** The agent implements a reviewed spec. It does not get to decide what a metric means or what grain a model is. Requirements are a human input, fixed before the build.
- **Portable by mandate.** Day arithmetic uses `{{ dbt.datediff(...) }}` and keys use `dbt_utils` macros, so these models compile unchanged on Snowflake or BigQuery. Nothing is locked to DuckDB except the connection.

## What this changes about team sizing — and what it doesn't

**What changes:** the implementation-to-specification ratio collapses. Twenty tested models across four business domains, from approved spec to merged PR, in a single working session. The mechanical labor of writing staging models, wiring `ref()`s, drafting tests, and reconciling row counts — the work that used to fill days — compresses to minutes. One engineer with this workflow covers ground that recently took a small team.

**What doesn't change:** every part of this build that mattered was human. Someone had to know that GMV is price plus freight, that a valid order is a delivered one, that the geolocation table fans out if you join it raw, and that a passing test can still assert nothing. Someone had to write those rules down *before* the agent ran, review the spec the agent produced, and treat a deprecation warning as a stop condition instead of noise. The agent did not decide any of that. It executed it, fast, and caught its own mechanical slips along the way.

The teams that get smaller are the ones doing mostly implementation. The judgment — what to measure, what "correct" means, where the silent bugs hide — does not compress. If anything it becomes the entire job. The value moves from *writing* the pipeline to *specifying and verifying* it, and that is a more senior skill, not a less necessary one.

That is the honest version of the pitch. Not "AI replaces the data team." Rather: **AI collapses the implementation half of the work, which makes the specification-and-verification half the whole job — and that half is where the engineering was all along.**

## Run it yourself

```bash
# 1. Clone
git clone https://github.com/stankidd/olist-dbt-claude.git
cd olist-dbt-claude

# 2. Install
pip install dbt-core dbt-duckdb duckdb kaggle

# 3. Load the data (needs a free Kaggle API token in ~/.kaggle/kaggle.json)
python scripts/load_data.py

# 4. Build everything
dbt build --profiles-dir .

# 5. Explore the marts
dbt show --profiles-dir . --inline "select * from main.mart_sellers limit 10"
```

Expected result: 20 models, 121 tests, a clean build in well under a minute.
